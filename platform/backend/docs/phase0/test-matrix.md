## 1. How to read this document

The matrix has two parts. Sections A to F describe each scenario: trigger, expected safe outcome, where it is enforced and what tests exist. Section G gives the **execution profile** for the same IDs: prerequisites, response mode, risk and policy outcome, expected Cortex call count, owner, follow-up phase and run status. Section H lists findings to take to Daniel.

**Overriding rule: fail closed.** When evidence is missing, a dependency is down, or an identity or integrity check fails, no Cortex action runs and the uncertainty is recorded. Fail closed does not mean "any failure blocks everything": a failure in an optional enrichment source (MISP) does not by itself block an action. Mandatory evidence, verification, risk, policy, approval and runtime gates still decide every action.

**Coverage status**
- `Covered`: a unit or integration test with a matching name exists.
- `Covered (conditional)`: the test exists but is skipped unless a live prerequisite is configured.
- `Partial`: part of the behavior is tested, and the part that is not is named in the row.
- `Gap`: no test found. Where the code also has no handler, the row says so.
- `Proposed`: the expected outcome is a proposal that needs agreement with Daniel before anyone implements it, because it touches shared code (`app/main.py`, graph nodes, runtime safeguards).

**Run status (Section G)**
- `Not run`: not executed by us at this commit.
- `Historical`: documented in the 12 Oct lab runs at commit `bdbc4e3` per the file guide. Not re-run, so it is not current verification.

**Target tier** uses the vocabulary in `evidence-classification.md`: Mock, Simulated, Isolated-live, Production-live.

## H. Findings to hand to Daniel

1. **TM-10 and TM-15** (Indexer failure, Ollama failure) have no handler in the code path read and no test. The safe outcome is still "no action", since nothing reaches policy, but the investigation may not be recorded. This was not executed, so confirm it empirically in Phase 5 before treating it as a bug.
2. **TM-34 and TM-37** are about actions that may already have executed. Today a timeout is stored as `failed`, and a database failure after a successful Cortex call can leave a `started` record with the action in effect. No reconciliation was found. Any fix touches shared runtime code, so Ahmad proposes the diff and tests and Daniel integrates.
3. **TM-13:** during a MISP outage the analysis prompt says "No MISP matches found." The failure is recorded in `misp_error` and the audit log, but it is not passed to the model, and an existing test asserts the "No MISP matches found." text. This overlaps Ahmad's Phase 5 task on explicit enrichment-failure behavior and the roadmap Phase 10 item about MISP outages not masquerading as healthy enrichment.
4. **TM-41:** evidence provenance is limited as described in the row. In particular, the persisted `captured_at` is the investigation completion time, not the retrieval time. Any schema change touches `app/schemas.py`, which is shared.
5. **TM-42:** the agent keeps no heartbeat, so an idle Wazuh cannot be told apart from a broken forwarder. Needs an owner. Alert silence must also not be read as an idle Cortex, because the expiry runner keeps working independently.
6. **TM-05** needs one explicit test that an ML error cannot take the benign fast path.
7. **TM-25 and TM-36** use two different environment variable names for the live PostgreSQL tests (`ATHENASEC_TEST_PG_URL` and `ATHENASEC_TEST_DATABASE_URL`). That is a likely reason some of the 9 skips are skipped, and it matters for the Phase 9 task on PostgreSQL-dependent skipped tests.
8. **TM-38 and TM-39:** no live run exists for a sufficient-evidence case, and the policy pipeline test starts from a stubbed verified analysis. Zero proposed actions is a valid result and has no explicit test.
9. **TM-40:** case IDs have a legacy alert-derived form plus V2 policy-denial, approval-resolution, runtime, and execution forms. Expected values in the Phase 5 ID-survival check must use the right derivation, and dedicated tests for every V2 case-ID derivation have not been established by this matrix.
10. **TM-04/TM-05:** ML loader failure or classifier exception produces `unknown` and `ml_error`, but the analysis verifier does not block solely on that error (it skips mismatch checking for an `unknown` ML prediction). Whether verified evidence could allow a V2 response needs explicit negative-path tests. If the safety requirement is zero Cortex calls for any ML failure, a deterministic execution-denial gate must be designed and tested in the assigned later phase; do not claim it already exists.
