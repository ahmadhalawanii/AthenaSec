Notes on the sources:

- There are two frontend copies: `AthenaSec-Ahmed-Website/website/frontend/src` (used here, as requested) and `AthenaSec/website/frontend/src`. **They are identical in content.** A plain `diff -rq` lists 7 files as different (`AdminStateProvider`, `ResponsePolicyProvider`, `SocStateProvider`, `TopBar`, `notificationsData`, `policyEngine`, `responsePolicyContext`), but `diff -rq --strip-trailing-cr` over the whole `src` tree reports no differences, and `diff --strip-trailing-cr` of `data/policyEngine.ts` and `data/notificationsData.ts` is empty. - `agent-integration.md`: the `src_ip` / `dst_ip` error was corrected in `AthenaSec-Ahmed-Website/website/docs/agent-integration.md` and the corrected file copied to `backend/docs/agent-integration.md` (byte-identical, checked with `cmp`).

Its IDs are sequential strings (`ALT-001`, `CASE-006`, `APR-001`, `EXE-001`, `AUD-206`, `REC-001`, `TKN-001`, `USR-001`) assigned client-side by `nextNumber()` / `nextId()` (`data/approvalFlow.ts`, `components/AdminStateProvider.tsx`). **Verified: `investigation_id` on `POST /analyze` is always null.** `analyze_alert` calls `run_investigation(alert)` with no `incident_id` (`main.py:2666-2676`). `run_investigation` only builds and stores an `investigation_id` when `incident_id is not None` (`main.py:1014-1033`). The graph never sets one: the only graph node that reads it, `assess_action_risk.py:66-90`, returns empty `proposed_actions` and `action_risk_assessments` when either id is missing. `persist_investigation_lifecycle` returns `None` when `investigation.incident_id is None` (`investigation_lifecycle.py:61-71`), so `main.py:1164-1175` never copies an id into the response. Consequences for `/analyze` results: `incident_id` and `investigation_id` are null, there are no proposed actions, risk assessments, policy decisions or approvals, and no `incident_investigations` row. The Wazuh route behaves the same when no ML classifier is configured (`main.py:2724-2727`, `run_investigation(alert)` with no incident). Wazuh alerts that pass through correlation get an incident id (`main.py:2760-2770`, `incident_id=correlation.incident.incident_id`); the benign branch (`run_benign_wazuh_investigation`) was not traced.

**Verified: action parameters, rollback fields and evidence links.**

- `ProposedActionRecord.parameters` holds either `{}` or exactly `{"duration_minutes": <int>}` (`response_proposal.py:368-381`, `_action_parameters`; it is `{}` when the proposal has no duration). The key is **`duration_minutes`**, the same name as `ResponseActionProposal.duration_minutes`, and the website's `params.duration_min` is the only name that differs. Nothing else is stored in `parameters`.
- `rollback_parameters` is always `{}` (`response_proposal.py:384-409`, `_rollback_fields`). `rollback_action_type` is `unblock_ip` for `block_ip`, `unlock_account` for `lock_account`, and `None` (with `reversible=False`) for `capture_telemetry`. Target and target type are separate fields (`target_type`, `target`), not parameters.
- The proposal ID takes `duration_minutes` as an input (`response_proposal.py:419-430`), so changing a duration yields a different `PACT-` id.
- **Where evidence refs go after the proposal stage:** they are checked once against the investigation's evidence IDs (`response_proposal.py:199-249`, `_validate_evidence_refs`) and are **not copied** into `ProposedActionRecord.parameters`, the action risk record or the policy decision record: `grep evidence_refs` over `backend/app` (excluding `schemas.py`) finds uses only in `graph/nodes/analyze.py` (the analysis step detail, line 479), `graph/nodes/verify_analysis.py`, `services/analysis_verifier.py`, `services/benign_investigation.py` and `services/response_proposal.py`. They survive in one place: the full proposal object stored on the response, `InvestigationResponse.response_proposal` (`schemas.py:606-616`, `StructuredResponseProposal.actions[].evidence_refs`; set at `main.py:1093-1097`), returned by `GET /investigations/{alert_id}`. `build_proposed_action_records` creates `proposed_actions` by `enumerate(proposal.actions, start=1)` (`response_proposal.py:~445-500`), so `proposed_actions[i]` corresponds to `response_proposal.actions[i]` by position. The position is not stored on `ProposedActionRecord`; the pairing relies on list order (open item in section 6).
- `action_fingerprint` hashes the proposed action without any evidence refs (see 1.6).

**Verified: `action_fingerprint` is not comparable to the website's `paramsDigest`.**

| | Agent `action_fingerprint` | Website `ApprovalToken.paramsDigest` |
|---|---|---|
| Source | `action_approval.py:24-87` `build_action_fingerprint` | `data/policyEngine.ts:829-831` `actionDigest`, `sha256Hex` and `canonicalJson` (lines 810-826) |
| Hashed object | `proposed_action_id`, `incident_id`, `investigation_id`, `action_type`, `target_type`, `target`, `parameters`, `reversible`, `rollback_action_type`, `rollback_parameters` | `{name, params}` only |
| Canonical JSON | Python `json.dumps(sort_keys=True, separators=(",",":"), ensure_ascii=False)` | JS recursive key-sorted `JSON.stringify` |
| Encoding | `sha256:` + 64 hex chars | 64 hex chars, no prefix |

Both are SHA-256 over key-sorted JSON that binds an approval to an exact action, but the inputs, key names and prefix differ, so the two values can never be equal for the same action. The agent's fingerprint also covers IDs that the website action does not have. The agent has no "token" object: nothing in `schemas.py` or the stores corresponds to `ApprovalToken` (`id`, `approverId`, `issuedAt`, `expiresAt`, `usedAt`). The fingerprint is checked by `approval_matches_action` (`action_approval.py:90-106`). Single-use is enforced on the agent by the one-way `PENDING` to decided transition (`store.transition_pending_approval`, `approval_resolution.py:105`), not by a token.

**Verified: unknown-id behaviour of `POST /approvals/{approval_id}/decision`.** Order: auth first (`require_approval_identity(allow_decision=True)`: 401 without identity, 403 without decide permission or CSRF), then body validation (422). `resolve_approval_request` raises `LookupError("Approval request was not found.")` when `store.get_approval_request` returns nothing (`approval_resolution.py:64-73`), and `decide_approval` maps it to **404** with `{"detail": "Approval request was not found."}` (`main.py:3115-3119`). The id is not echoed. `ValueError` becomes **409** (`main.py:3120-3125`): the approval references a missing proposed action (`approval_resolution.py:81-85`), the approval was already decided or changed (`approval_resolution.py:105-108`), or a rule raised inside `decide_approval_request` (that function was not read).

## 3. Lookup rules (what each route accepts and returns for an unknown id)

| Route | Accepts | Unknown id | Auth |
|---|---|---|---|
| `GET /alerts` | filters `status`, `classification`, `since` (no id filter) | n/a (empty list) | Read |
| `GET /investigations` | filters `status`, `incident_id` | unknown `incident_id` gives `{total:0, items:[]}` | Read |
| `GET /alerts/{alert_id}` | alert id only. `store.get(alert_id)`; returns `AlertDetail` (the list entry plus `normalized_event`, `event_text`, `ml_error`, MISP fields). `event_text` is null when no incident alert record exists | 404 `"Alert {alert_id} was not found."` | Read |
| `GET /investigations/{id}` | **alert id or `INV-...` id.** Tries `store.get(id)` (`investigations.alert_id`) first; if that misses, looks `id` up as an incident investigation (`get_incident_investigation`) and returns the investigation of its `primary_alert_id`. Alert id wins if a value matches both. (`POST /analyze` results carry `incident_id` and `investigation_id` as null, see 1.3.) | 404 `{"detail":"Investigation {id} was not found."}` (also when an `INV-` record exists but its primary alert has no investigation) | **None** (the handler calls no `require_approval_identity`) |
| `GET /investigations/{alert_id}/case` | alert id; returns the **legacy** `CaseRecord` (not the `Case` from `/cases`) | 404 `"Case for investigation {alert_id} was not found."` | None |
| `GET /investigations/{alert_id}/audit` | alert id | **200 with `[]`** (no existence check) | None |
| `GET /approvals/{approval_id}` | approval id only | 404 `"Approval request was not found."` (the id is not echoed) | Read |
| `POST /approvals/{approval_id}/decision` | approval id | 404 `"Approval request was not found."`; 409 for a missing proposed action or an already decided approval (`approval_resolution.py:64-108`, `main.py:3115-3125`) | Decide + CSRF |
| `GET /cases` | filters incl. `incident_id`, `alert_id`, `assigned_analyst`, `status`, `q` | empty list | Read |
| `GET /cases/{case_id}` | case id; reads `incident_cases` only (legacy `cases` table is not exposed here) | 404 `"Case {case_id} was not found."` | Read |
| `GET /audit` | filters `incident_id`, `alert_id`, and others; `alert_id` also fills `alert_events` | empty list | Admin |
| `GET /audit/{event_id}` | operator `OPAUD-...` id, then incident `AUD-...` id | 404 `"Audit event {event_id} was not found."` | Admin |

Not available: any route keyed by incident id, evidence id, proposed action id or response action id. Error format is FastAPI `{"detail": "<string>"}`; 422 for query/body validation uses FastAPI's list-shaped `detail` (plan section 0 and 7).

## 4. Inconsistencies

1. **Action vocabulary (website vs agent).**
   - Agent (`schemas.py`): proposals are `block_ip`, `lock_account`, `capture_telemetry` (`ResponseProposalActionType`); the wider `AllowedAction` adds `notify_administrator`, `create_case`, `record_response`; `ProposedActionRecord.action_type` is a plain string.
   - Website: `Tier2ActionName` = `block_ip`, `isolate_host`, `suspend_user_session`, `kill_process`, `quarantine_file`, `reset_password`; `ActionType` (display, `incidentResponseTypes.ts`) = `'Block IP'` | `'Isolate Host'`.
   - Only `block_ip` exists on both sides. `isolate_host`, `suspend_user_session`, `kill_process`, `quarantine_file`, `reset_password` have no agent counterpart; `lock_account` and `capture_telemetry` have no website counterpart. Whether `lock_account` equals `suspend_user_session` or `reset_password` is not stated anywhere.
   - Status: plan section 6 item 11 / section 7 decision 4: **unresolved, blocks the approvals page.** `agent-integration.md` section 6 says the same.
2. **Action parameter names.** Agent `duration_minutes` (`ResponseActionProposal`); website `params.duration_min` (`data/approvalData.ts`). Verified: the agent stores exactly `{}` or `{"duration_minutes": n}` in `ProposedActionRecord.parameters` and `{}` in `rollback_parameters` (`response_proposal.py:368-409`). The website's `params` carry more keys (`ip`, `host`, `path`, `duration_min`, per `policyEngine.ts` proposals), none of which exist on the agent side; the target is the separate `target` field.
3. **Case ID: one prefix, five seeds.** `CASE-` + UUID5 is built from: `"athenasec-case:{alert_id}"` (legacy `case_service.py`), `"athenasec-approval-case:{approval_id}:{status}"` (`approval_resolution.py`), `"athenasec-execution-case:{response_action_id}:{reason}"` (`structured_execution.py`), `"athenasec-policy-case:..."` (`structured_action_policy.py`), `"athenasec-runtime-case:..."` (`structured_response_runtime.py`). Legacy cases live in `cases` and are served only by `/investigations/{alert_id}/case`; the other four write `incident_cases`, served by `/cases`. The same alert can therefore have a legacy case and an `incident_cases` case with different IDs. Website: `CASE-006` (sequential, client-assigned).
4. **Case shape.** Legacy `CaseRecord` (`case_id, alert_id, policy_id, classification, risk_score, risk_band, status, reason`) vs `Case` from `/cases` (adds `incident_id`, `investigation_id`, `assigned_analyst`, ...). Status: agent `IncidentCaseStatus` = `open / investigating / contained / resolved / closed`; legacy `CaseStatus` = `open` only (per `agent-integration.md`); website `CaseStatus` = `'Open' | 'Closed'`. Severity: website `CaseSeverity` = `Medium / High / Critical` and `AlertRecord.severity` = `Low / Medium / High / Critical` (capitalised); agent `RiskBand` = `low / medium / high / critical` (`schemas.py:59-64`), identical to the website's own `RiskBand` type (`alertsTypes.ts`). A capitalising transform from `risk_band` to `severity` is plausible but no code or document defines it, and `CaseSeverity` has no `Low`.
5. **Audit ID formats.** Agent: incident and legacy audit `AUD-` + **UUID4** upper-case (`audit_service.py`); operator audit `OPAUD-` + UUID4 hex (`operator_audit_store.py:192`). Website: `AUD-206`, sequential, with `numberOf(log)` parsing the number from the ID (`data/auditChain.ts:18`), so it will break on an `AUD-<uuid>` value. Website hashes its own chain client-side; the agent's chain is `operator_audit_events` (`prev_hash`, `row_hash`).
6. **Audit event shape.** Website `AuditLogRecord`: `id, timestamp, user, role (Analyst/Administrator/System), category, action, target, result, sourceIp, description, changes[], metadata{}, eventType?, record?`. Agent `AuditEvent`: `event_id, occurred_at, actor_id, actor_role (AuditActorRole), category, action, target, result, source_ip, source, incident_id, detail{}, prev_hash, row_hash`. The seven website `AuditEventType` values (`recommendation_created`, `decision_recorded`, `action_executed`, ...) are not the agent's `AuditEventType` (`investigation_created`, `policy_evaluated`, `case_created`, `cortex_execution_started`, ...) nor `IncidentAuditRecord.event_type` (free string).
7. **Recommendation vs approval vs proposed action.** Website has three IDs where the agent has two-and-a-half: `Recommendation.id` (`REC-nnn`), `ApprovalRecord.id` (`APR-nnn`), `ApprovalToken.id` (`TKN-nnn`). Agent has `proposed_action_id` (`PACT-`) and `approval_id` (`APR-`, with `action_fingerprint`). `Recommendation` has no one-to-one agent object, and `TKN-` has none (the closest candidate, `action_fingerprint`, is not comparable: different inputs and format, see 1.6).
8. **Approval status.** Agent upper-case `PENDING / APPROVED / REJECTED / EXPIRED / CANCELLED`; website `'Pending' | 'Approved' | 'Rejected' | 'Timed out'` (no `CANCELLED`).
9. **Decider.** Agent `decided_by: string` (operator id); website `decidedBy: {id, name, role}` with role `soc_analyst | soc_lead`. Agent roles for browser users are `Analyst / Administrator` (plan section 2.1); bearer operators have no role. (`AuditActorRole` = `Analyst / Administrator / System`, `schemas.py:1509-1513`, equals the website `AuditLogRecord.role` set; `AuditResult` = `Success / Failed / Denied`, `schemas.py:1503-1507`, equals the website `AuditResult`. These two match.)
10. **Alert ID format.** Agent: caller-supplied or `"{index}:{doc id}"` / `"wazuh:{id}"`. Website: `ALT-nnn`. Not convertible.
11. **Alert status and ownership.** Agent `AlertListEntry.status` is the **pipeline** status (string); website `AlertStatus` is `Open | Closed` with `assignedAnalyst`. Plan answer 8: alert assign/close is out of scope, so these stay mock.
12. **Alert metadata key names.** `agent-integration.md` section 4 said `src_ip`, `dst_ip`, `agent_name`. The parser writes `source_ip`, `destination_ip`, `agent_name`. **Corrected** in the website doc and in `backend/docs/agent-integration.md`. (`case_view.py` already reads `source_ip` and `agent_name`.)
13. **Evidence tag enums.** See 1.4: website `Auth / Intel / Endpoint / Network / Response / Policy`; agent `EvidenceSource` and `EvidenceType` differ.
14. **Field renames already settled** (plan section 6 item 3, built in `Case`): `assigned_analyst`, `recommended_actions`, `mitre_ids`, `endpoint`, `source_ip`, `evidence` use website names. Remaining case differences: website `id` vs agent `case_id`; website `lastUpdated`/`createdAt` strings like `Today, 14:34` vs ISO datetimes; website `mitre: string` vs agent `mitre_ids: string[]`; `CaseAction` has no `position`/`proposed_action_id` on the website.
15. **Entity-type vocabulary.** `IncidentAuditEntityType` has 15 values (`schemas.py:1011-1027`): `incident, alert, investigation, evidence, incident_risk, proposed_action, action_risk, policy_decision, approval_request, response_action, action_result, case, verification, rollback, containment_expiry`. The website has no matching concept (its audit `target` is free text).
16. **Investigation route parameter naming.** `GET /investigations/{alert_id}` now accepts an alert id or an `INV-...` id (section 3), but the path variable in `main.py` is still named `alert_id`, so the OpenAPI parameter name is misleading. The response is always the investigation of the primary alert, keyed by `alert_id`.
17. **Missing auth on three investigation routes** (not an ID mapping issue, but it determines who can resolve an ID): `GET /investigations/{alert_id}`, `/case`, `/audit` call no `require_approval_identity`, while `GET /investigations` does.

## 7. Security finding: three investigation routes have no authentication

**Not changed.** This section records the finding only; no code was modified.

- **Routes** (`backend/app/main.py:2986-3043`):
  - `GET /api/v1/investigations/{alert_id}`
  - `GET /api/v1/investigations/{alert_id}/case`
  - `GET /api/v1/investigations/{alert_id}/audit`
- **Evidence:** the handlers `get_investigation(alert_id)`, `get_case_for_investigation(alert_id)` and `get_investigation_audit_history(alert_id)` take only the path parameter. None has an `authorization`/`request` argument or calls `require_approval_identity`. Compare `GET /api/v1/investigations` (list), `GET /api/v1/alerts` and `GET /api/v1/approvals/{id}`, which do (`main.py:2908`, `2952`, `3057`).
- **What they return:** the full `InvestigationResponse` (normalized event text, `alert_metadata` including source and destination IPs, usernames and agent names, ML and MISP results, evidence records, proposed actions, risk and policy decisions, approval requests); the legacy case; and the per-alert audit trail. Alert IDs are not secret (Wazuh ids are `{index}:{_id}`), so knowing one is enough.
- **Related, observed while reading and also not changed:** `POST /api/v1/analyze` (`main.py:2666-2676`) takes no auth parameter and runs the whole investigation pipeline, and `GET /health` also takes none (its intent was not checked). This was not reviewed further.
- **Why it matters for this mapping:** the lookup rules in section 3 describe these routes as open. If auth is added later, the website adapter will need credentials (cookie or bearer) on these calls, and the plan's `Read` permission would be the natural level.
- **Status:** reported only. A fix is a code change and is outside this task.
